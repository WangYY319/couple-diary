登录历史与配对流程

正常登录流程（首次）

1
选择角色 → 用户在入口页选择 TAO 或 YAN
2
自动配对 → Pair.autoJoin(role) 使用默认配对码 U2A6KA 加入
3
写入本地 → pairCode 和 role 保存到 LocalStorage + IndexedDB 双重备份
4
进入应用 → enterAfterPair() 启动云同步 + 10秒轮询

正常回访（缓存完好）

1
Cloud.init() → 从 LocalStorage 读取 ty_pairCode → 找到
2
验证角色 → 从 LocalStorage 读取 ty_role → 找到
3
直接进入 → enterApp() 启动云同步和轮询
4
实时互动 → 每10秒轮询 syncToday() + syncQuizVocab() 等

清缓存后登录（出问题的场景）

1
LocalStorage 全部清除 → pairCode、role、所有日记数据、问答答案、配对历史 → 全部丢失
2
IndexedDB 可能被清除 → 取决于浏览器"清除数据"的范围
• 仅"清除缓存"：IndexedDB 保留 → 可恢复 pairCode
• "清除所有数据"：IndexedDB 也清除 → pairCode 备份丢失
3
Cloud.init() 尝试恢复 → LocalStorage 无 pairCode → 查 IndexedDB 备份
4
如果 IndexedDB 有备份 → 恢复 pairCode 和 role → 进入应用
5
如果 IndexedDB 也清除 → 显示入口页 → 用户选角色 → autoJoin() 重新加入配对码 U2A6KA

根因分析：为什么无法实时互动

清缓存后虽然能重新进入应用（通过 IndexedDB 备份或重新加入配对码），但实时互动会中断。以下是4个根因：

根因1：pushQuizVocab() 用空数据覆盖云端（最严重）

问题：清缓存后本地问答答案为空 []。syncQuizVocab() 先执行 pushQuizVocab()，将空答案推送到云端，覆盖了之前存储的答题数据。

影响：对方在下次轮询（10秒后）拉取到空数据，显示"对方未答题"，已答题的进度丢失。

// 修复前的代码流程 syncQuizVocab() { await pushQuizVocab(); // ← 推送空数据到云端，覆盖！ remote = await pullQuizVocab(); // 拉取对方数据 }

根因2：pushAllDays() 可能用空数据覆盖云端日记备份

问题：清缓存后本地日记数据为空。syncAll() 虽然先拉取 days_all 并合并，但如果拉取失败（网络抖动），pushAllDays() 会用空数据覆盖云端备份。

影响：云端 days_all 变为空，双方的日记数据永久丢失。

根因3：ns_cleanup_v108 标志丢失，导致重复清理

问题：清缓存后 LocalStorage 中的 ty_ns_cleanup_v108 标志丢失。syncAll() 调用 cleanupOldNamespace() 时，检测到标志不存在，重复执行旧命名空间数据清理。

影响：虽然主要清理旧数据，但重复执行可能触发额外的网络请求和延迟，影响同步性能。

根因4：IndexedDB 数据也被清除导致照片/语音丢失

问题：部分浏览器"清除所有站点数据"会同时清除 IndexedDB（couple_pwa_db 照片库、couple_letter_db 信件库）。虽然云端仍有备份，但需要重新下载，量大时耗时较长。

影响：对方的照片和语音在本地消失，需要从云端逐个下载恢复，期间界面显示为空。

根因严重度数据丢失风险实时互动影响
pushQuizVocab 覆盖空数据致命答题进度丢失对方看到"未答题"
pushAllDays 覆盖空数据致命日记数据丢失日记内容消失
ns_cleanup 重复执行中等无直接丢失同步延迟增加
IndexedDB 被清除中等需重新下载照片/语音暂时为空
🔧
已实施的修复（v117）

修复前

pushQuizVocab() 直接推送空数据
→ 云端被覆盖
→ 对方拉到空数据
→ 实时互动中断

修复后

pushQuizVocab() 先拉取云端旧数据
→ 本地为空但云端有数据 → 恢复
→ 推送恢复后的完整数据
→ 实时互动正常

修复1：pushQuizVocab() 增加"先拉后推"保护

在推送前先拉取云端已有的自己的数据。如果本地为空但云端有数据，说明是清缓存场景，先用云端数据恢复本地，再推送恢复后的完整数据。

// 修复后 async pushQuizVocab() { // 先拉取云端已有的数据 const existing = await fetch(...); if (quizAnswers.length === 0 && existing.quizAnswers.length > 0) { // 检测到清缓存，用云端恢复 Store.set('quiz_a_...', existing.quizAnswers); needRestore = true; } if (needRestore) { // 推送恢复后的完整数据 await POST(restoredData); return; } // 正常推送 await POST(localData); }

修复2：pushAllDays() 增加空数据保护

当本地日记数据为空时，不再直接推送空数据。而是先从云端拉取 days_all 恢复到本地，避免用空数据覆盖云端。

修复3：Cloud.init() 增加 isFreshLogin 标记

当检测到配对码从 IndexedDB 备份恢复（而非 LocalStorage 直接读取），标记 isFreshLogin = true，后续同步逻辑可据此优先从云端拉取而非推送。

规避建议

日常使用建议

建议原因操作方法
不要清除站点数据 清除缓存会删除 LocalStorage 中的配对码和所有本地数据 如需清理空间，仅清除"缓存图片和文件"，不要勾选"Cookie和网站数据"
统一通过浏览器访问 桌面PWA有独立存储分区，与浏览器数据不共享 通过 https://wangyy319.github.io/couple-diary/ 直接访问
不要清除IndexedDB IndexedDB存储配对码备份和照片/语音/信件 浏览器设置中"清除数据"时，确保未勾选"IndexedDB"
清缓存后先等待同步 重新进入后需要从云端拉取数据恢复 进入应用后等待5-10秒，看到数据恢复后再操作

如果已经出现无法互动的情况

1
双方都刷新页面 → 等待 Service Worker 更新到 v117
2
清缓存的一方重新进入 → 系统会自动从云端恢复答题数据和日记数据
3
等待10-20秒 → 轮询同步恢复后，双方即可恢复实时互动
4
验证 → 在一方操作答题或写日记，另一方应在10秒内看到更新

存储层级与清缓存影响对照

存储位置存储内容清缓存影响恢复机制
LocalStorage 配对码、角色、日记、问答答案 必清 IndexedDB备份 + 云端同步
IndexedDB (couple_backup_db) 配对码和角色的备份 可能清除 重新通过配对码 U2A6KA 加入
IndexedDB (couple_pwa_db) 照片、语音二进制数据 可能清除 从云端逐个下载恢复
IndexedDB (couple_letter_db) 信件数据 可能清除 从云端同步恢复
Service Worker Cache HTML/CSS/JS 静态文件 可清 下次访问自动重新缓存
云端 MantleDB 所有同步数据的云端备份 不受影响 无需恢复

核心结论：清缓存后的数据恢复依赖于云端备份。v117 修复后，即使本地数据被清空，系统会先从云端拉取恢复，再用恢复后的完整数据推送，不会再用空数据覆盖云端。双方刷新到 v117 后即可恢复实时互动。
