问题1：未操作但已有答案

现象描述

对方反馈安卓手机打开后，趣味问答和亲密问答板块存在未填写但已有回答过的问题。疑问是否系统自动操作或有人入侵。

根因分析

结论：不是系统自动操作，也不是被入侵。是云同步逻辑的 bug 导致的"幽灵答案"。

根因A：v117 的 pushQuizVocab 恢复逻辑误恢复

上一版本修复"清缓存后空数据覆盖云端"时，在 pushQuizVocab 中添加了"先拉取云端旧数据恢复本地"的逻辑。但这个恢复使用的是 App.currentRole：

// v117 代码 if (quizAnswers.length === 0 && existing.quizAnswers.length > 0) { Store.set(`quiz_a_${ds}_${role}`, existing.quizAnswers); // role = App.currentRole }

如果对方清缓存后重新登录，但角色选择与之前不同（例如之前是TAO，清缓存后选了YAN），恢复逻辑会将 TAO的答题数据恢复到YAN的存储槽位，导致YAN看起来"已有答案"。

根因B：syncQuizVocab 的拉取逻辑角色交叉

pullQuizVocab() 拉取的是 "对方角色" 的数据：

// 代码逻辑 const otherRole = App.currentRole === 'TAO' ? 'YAN' : 'TAO'; const r = await fetch(this._url(`extra/${ds}/${otherRole}`, qaNs));

如果本地角色被错误设置（清缓存后角色恢复不正确），拉取到的"对方数据"实际是自己的数据，然后存入对方的存储槽位。这导致界面显示"对方已答题"，但实际是自己的旧答案。

根因C：问答题目缓存被错误恢复

清缓存后 quiz_q_${dateStr}（今日题目）为空。如果 v117 的恢复逻辑从云端拉取了旧题目缓存并恢复，而这些题目可能是前几天的旧题目，与今日实际应生成的题目不同。用户看到的是旧题目的旧答案，以为是今天"已有答案"。

排除安全风险

排查项结论依据
是否有人入侵网站否GitHub Pages 是静态托管，无法被入侵。配对码 U2A6KA 虽然是公开的，但只有知道这个码的人才能访问云端数据
是否系统自动答题否系统没有任何自动答题逻辑，所有答案都是用户点击选择后通过 _answer() 方法保存的
是否MantleDB被篡改否MantleDB 是按命名空间隔离的KV存储，配对码一致的命名空间只有你们两人能写
配对码是否泄露低风险U2A6KA 是固定默认码，如果有第三方知道此码理论上可访问你们的命名空间数据。但无法影响你们的本地界面

问题2：配对码一致但数据完全分离

现象描述

对方登录后，虽然设置里配对码一致（都是 U2A6KA），但界面数据完全分离，看不到彼此的数据，仿佛在两个不同的空间。

根因分析

根因1：角色恢复不一致（最核心原因）

你们两人使用固定配对码 U2A6KA，一个选 TAO，一个选 YAN。云端数据结构是：

命名空间: couple-pwa-u2a6ka ├── days_all (双方日记，按角色字段区分: greet.tao / greet.yan) ├── meta (配对元数据) └── qa-2026Q3 命名空间 ├── extra/2026-08-24/TAO (TAO的问答答案) └── extra/2026-08-24/YAN (YAN的问答答案)

如果对方清缓存后，角色信息丢失，重新选择时选了与你相同的角色（例如都选了TAO），那么：

  • 他推送数据到 extra/.../TAO → 覆盖了你的TAO数据
  • 他拉取"对方数据"时拉取 extra/.../YAN → 拉到的是空（因为你不是YAN）
  • 他看不到你的数据，你也看不到他的
  • 数据完全分离

根因2：清缓存后本地数据丢失，syncAll 恢复不完整

清缓存后 LocalStorage 全部清空。syncAll() 从云端拉取 days_all 并合并到本地，但：

  • 如果 days_all 之前被 v117 的 bug 用空数据覆盖过 → 云端也为空
  • 如果网络不稳定，pullAllDays() 失败 → 本地保持为空
  • pushAllDays() 在本地为空时又用空数据覆盖云端 → 恶性循环

根因3：安卓浏览器存储策略更激进

安卓 Chrome 的"清除浏览数据"默认会清除 LocalStorage + IndexedDB + Service Worker Cache，比 iOS Safari 更彻底。iOS Safari 的"清除历史记录与网站数据"有时只清除部分缓存，IndexedDB 可能保留。这就是为什么你的苹果手机正常，对方的安卓出问题。

数据分离的流程图

1
对方清缓存 → LocalStorage 全清 → pairCode、role、所有本地数据丢失
2
IndexedDB 也被清（安卓Chrome默认行为）→ 备份也丢失
3
重新打开网站 → Cloud.init() 无法恢复 → 显示入口页选角色
4
选了与之前不同的角色（或不记得之前选的什么）→ 角色冲突
5
autoJoin 用新角色加入 → joinPair 写入 meta → 角色可能与你的重复
6
syncQuizVocab 拉取"对方"数据 → 实际拉到的是自己的旧数据或空数据
7
pushQuizVocab 推送"自己"数据 → 覆盖了云端正确角色的数据
8
数据完全分离 → 双方看不到彼此的数据
🔧
v118 修复方案

修复1：syncQuizVocab 清缓存优先拉取

当 isFreshLogin = true 时，syncQuizVocab() 先拉取对方数据恢复本地，确保本地有对方数据后再推送自己数据。避免角色交叉导致的数据污染。

// 修复后 async syncQuizVocab() { if (this.isFreshLogin) { // 先拉取对方数据 const remote = await this.pullQuizVocab(); if (remote.quizAnswers?.length > 0) Store.set(`quiz_a_${ds}_${otherRole}`, remote.quizAnswers); } // 再推送（已有防空数据覆盖保护） await this.pushQuizVocab(); }

修复2：syncAll 增加数据量安全检查

在 pushAllDays() 前增加检查：如果本地数据量明显少于云端（<50%），说明恢复不完整，跳过推送，防止用不完整数据覆盖云端。

修复3：joinPair 标记 isFreshLogin

重新加入配对时标记 isFreshLogin = true，同时记录角色最后登录时间到 meta，后续可用于角色冲突检测。

修复4：enterAfterPair 确保先拉后推

配对成功后，确保 syncAll()（拉取恢复）完成后再执行 syncQuizVocab()（推送），避免恢复不完整时推送覆盖。恢复完成后清除 isFreshLogin 标记。

长期方案与风险说明

当前架构的固有风险

风险严重度说明
角色无绑定验证 高 配对码 U2A6KA 是公开的，角色选择由用户手动操作。如果有人选了与你相同的角色加入，会覆盖你的数据。当前没有任何机制阻止两个人选同一个角色
配对码公开可见 中 U2A6KA 写死在代码中，任何查看网页源码的人都能看到。虽然 MantleDB 命名空间隔离，但知道码的人可以读取/写入你们的云端数据
清缓存=数据重置 高 LocalStorage 和 IndexedDB 都被清除后，本地数据完全丢失。虽然云端有备份，但恢复依赖网络稳定性和同步逻辑正确性。任何一步出错就可能导致数据分离
无操作审计日志 中 无法追踪谁在什么时间做了什么操作。当数据异常时，无法确定是bug还是人为
MantleDB 无权限控制 中 云端存储 MantleDB 是公开的KV存储，任何知道命名空间的人都可以读写。没有鉴权机制

建议的长期改进方向

改进项优先级实施方案
角色绑定机制 高 创建配对时为每个角色生成唯一token，加入时必须提供对应token。防止两人选同一角色。可通过 meta 中存储角色token实现
配对码加密 中 将固定配对码改为用户自定义配对码（自定义6位码），不写死在代码中。虽然 MantleDB 无鉴权，但自定义码降低了被猜测的风险
操作日志 中 在云端记录关键操作日志（登录、答题、清缓存恢复等），便于排查异常
数据版本快照 低 每次 syncAll 后保存一个数据快照到云端（按日期），出问题时可回滚到之前的版本
角色冲突检测提示 高 加入配对时检查 meta 中的 lastTaoLogin / lastYanLogin 时间。如果对方近期活跃于同一角色，提示用户"此角色已被对方使用，请选择另一角色"

立即可执行的规避措施

1
双方确认各自的角色：你用TAO，对方用YAN（或反过来）。在设置页可以看到当前角色。如果角色重复，让对方重新选择正确角色
2
对方刷新到v118：清缓存后重新打开网站，Service Worker会自动更新到v118，修复角色交叉和数据覆盖问题
3
对方手动点🔄同步：进入应用后点击右上角同步按钮，强制拉取云端完整数据
4
不要清除"所有数据"：安卓浏览器清理时只选"缓存图片和文件"，不选"Cookie和网站数据"

重要提醒：如果对方当前角色与你相同（都是TAO或都是YAN），请让对方在入口页重新选择正确的角色（YAN）。角色不一致是导致数据分离的最直接原因。双方刷新到v118后，点击🔄强制同步即可恢复。
